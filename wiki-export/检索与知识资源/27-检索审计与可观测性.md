# 检索审计与可观测性

检索审计模块负责记录一次教材检索的请求上下文、检索策略、性能指标、命中证据及其来源信息，并提供按 `queryId` 查询完整检索记录的 HTTP 接口。它位于教材检索主流程之后，使用统一的 `RetrievalAuditEvent` 表达一次检索，再通过不同 Sink 写入持久化数据库或近期内存存储。

该模块的核心目标是让一次检索具备可追踪性：

- 能确认请求由谁、从哪个客户端、通过哪个接口发起。
- 能还原当时使用的检索策略和请求的 Top K。
- 能查看实际返回的命中数量、排序、分数和页面来源。
- 能分析检索耗时及页面质量。
- 能通过 `queryId` 查询一次完整的查询记录及命中证据。

## 模块职责

### 请求上下文规范化

`RetrievalRequestContext` 表示检索请求的调用方和设备线索，字段包括：

- `tenantId`：租户标识，当前默认值为 `default`，为后续学校或机构隔离预留。
- `subjectType`：主体类型，例如 `guest`、`student`、`teacher`、`admin` 或 `api_key`。
- `subjectId`：主体 ID，登录体系尚未接入时可以为空。
- `ip`：客户端 IP。
- `deviceId`：设备标识。
- `userAgent`：客户端 User-Agent。
- `endpoint`：触发检索的 API 路径。

上下文通过 `normalize()` 统一处理：

- 空白租户使用 `default`。
- 空白主体、IP、设备、User-Agent 会转换为 `null`。
- 空白 endpoint 使用 `/api/retrieval/textbooks/search`。
- 非空字符串会先执行 `strip()`。

`toAuditMap()` 将规范化后的字段转换为审计 JSON 使用的键值结构。空值不会写入 Map，因此数据库中的 `request_context_json` 只保留实际存在的请求线索。

默认上下文由 `defaultTextbookSearch()` 创建，适用于调用方没有显式传入审计上下文的教材文本检索场景。

### 审计事件建模

`RetrievalAuditEvent` 是一次教材检索的完整审计模型，对应两类数据库记录：

- `retrieval_query_log`：一次查询的汇总记录。
- `retrieval_hit_log`：该查询返回的每条命中记录。

事件字段包括：

- `queryId`：查询审计 ID，同时作为前端可使用的本次检索 trace ID。
- 租户和主体信息。
- 原始检索词 `queryText`。
- 总体检索策略 `retrievalStrategy`。
- 请求的 `requestedLimit`。
- 实际命中数量 `hitCount`。
- 检索耗时 `elapsedMs`。
- 请求上下文。
- 按排名排列的 `RetrievalAuditHit` 列表。

事件通过 `RetrievalAuditEvent.from(...)` 从检索请求和响应构建：

1. 请求上下文为空时使用默认教材检索上下文。
2. 非空上下文先规范化。
3. 响应中的命中结果按列表顺序转换为审计命中。
4. 排名从 `1` 开始。
5. 实际命中数取响应中的命中数量，而不是请求的 Top K。
6. 负数耗时被归一化为 `0`。

因此，审计事件同时保留了“用户要求返回多少条”和“实际返回多少条”两个维度，便于区分请求限制与检索结果质量。

## 调用链

源码证据明确了审计模型、Sink 和查询接口之间的调用关系；教材检索服务具体在哪一行触发 `record`，当前证据未展示。基于现有类型关系，其职责链如下：

```mermaid
flowchart LR
    A[教材检索请求] --> B[教材检索流程]
    B --> C[TextbookSearchResponse]
    C --> D[RetrievalAuditEvent.from]
    D --> E[RetrievalAuditSink.record]
    E --> F[RecentRetrievalAuditStore]
    E --> G[JdbcRetrievalAuditSink]
    H[GET /api/retrieval/audit/{queryId}] --> I[RetrievalAuditLookup.findByQueryId]
    I --> G
    G --> J[查询记录与命中记录]
    J --> H
```

关键节点：

- `RetrievalAuditEvent.from` 将检索请求、响应、耗时和请求上下文汇总成不可变审计事件。
- `RetrievalAuditSink` 是写入扩展点。
- `CompositeRetrievalAuditSink` 可以把一个事件转发给多个 Sink。
- `JdbcRetrievalAuditSink` 同时实现写入接口 `RetrievalAuditSink` 和查询接口 `RetrievalAuditLookup`。
- 审计查询接口通过 `RetrievalAuditLookup` 解耦控制器与底层存储实现。
- `RecentRetrievalAuditStore` 出现在 retrieval 模块中，并由组合配置用于近期记录能力；当前已读证据未展示其具体容量、淘汰策略或查询接口实现。

## JDBC 持久化

`JdbcRetrievalAuditSink` 使用 MySQL JDBC 直接完成审计写入和查询。

### 写入事务

一次 `record(event)` 使用一个数据库连接，并显式关闭自动提交：

1. 插入 `retrieval_query_log`。
2. 批量插入该查询的所有 `retrieval_hit_log`。
3. 两部分全部成功后提交事务。
4. 任一步骤抛出 SQL 异常或运行时异常时回滚。
5. 数据库连接最终关闭，并恢复原始的 auto-commit 状态。

该事务边界保证查询汇总记录和命中记录不会在正常异常路径下被静默拆开。写入失败会继续向上抛出 `IllegalStateException`，不会被 Sink 内部吞掉。

查询表写入的主要字段包括：

- `query_id`
- `tenant_id`
- `subject_type`
- `subject_id`
- `query_text`
- `retrieval_strategy`
- `requested_limit`
- `hit_count`
- `elapsed_ms`
- `request_context_json`

命中表写入的主要字段包括：

- `query_id`
- `rank_no`
- `chunk_id`
- `doc_id`
- `book_name`
- `page_no`
- `printed_page_no`
- `score`
- `retrieval_strategy`
- `page_quality_label`
- `source_page_image`
- `evidence_json`

### 命中证据

`evidence_json` 保存命中附加证据，查询时会解析以下字段：

- `volume`
- `chapter_path`
- `section_title`
- `text_snippet`
- `formula_text`

`chapter_path` 只有在 JSON 值确实为 List 时才转换为字符串列表，否则返回空列表。其他非空对象通过 `String.valueOf` 转换为字符串。

### 数据库查询

`findByQueryId(queryId)` 的行为如下：

- `queryId` 为空或全为空白时直接返回 `Optional.empty()`。
- 非空 ID 会先执行 `strip()`。
- 先查询 `retrieval_query_log`。
- 查询不到汇总记录时返回空结果，不再查询命中记录。
- 查询到汇总记录后，再按 `rank_no ASC` 查询所有命中。
- 最终重新组装包含命中列表的 `RetrievalAuditEvent`。

数据库中的空页码通过 `nullableInteger` 保持为 `null`，避免把 SQL NULL 错误还原成页码 `0`。

## 内存与 JDBC 组合 Sink

`CompositeRetrievalAuditSink` 接收一个 Sink 列表，并在 `record` 时按列表顺序逐个调用：

```java
for (RetrievalAuditSink delegate : delegates) {
    delegate.record(event);
}
```

组合器会对传入列表执行不可变复制，避免外部后续修改 delegate 列表。

当前组合策略的语义是同步广播：

- 事件可以同时写入近期内存存储和 MySQL。
- delegate 按配置顺序执行。
- 任意 delegate 失败都会向上抛出。
- 后续 delegate 不会继续执行。
- 已经成功写入的前置 Sink 不会由组合器自动补偿或回滚。

因此，组合 Sink 的一致性边界只覆盖单个 delegate 内部。JDBC Sink 自身具备查询表和命中表之间的事务性，但无法回滚另一个已经成功完成的内存 Sink。

这种失败策略明确避免了“检索已经完成但审计静默丢失”的情况，同时也意味着审计写入失败可能影响调用方对检索请求的整体结果处理，需要由上层决定是否将审计故障视为请求失败。

## 审计查询 API

`RetrievalAuditController` 暴露：

```text
GET /api/retrieval/audit/{queryId}
```

控制器只依赖 `RetrievalAuditLookup`：

1. 接收路径参数 `queryId`。
2. 调用 `findByQueryId(queryId)`。
3. 找到记录时直接返回 `RetrievalAuditEvent`。
4. 找不到记录时返回 HTTP `404 NOT_FOUND`，并附带包含 query ID 的错误信息。

控制器不直接依赖 JDBC 类，因此可以替换为内存查询、测试替身或其他持久化实现。当前证据显示 JDBC Sink 同时承担 `RetrievalAuditLookup` 实现，但接口分离保留了查询侧的替换空间。

## 关键状态与边界条件

### 请求上下文

- 租户为空或空白时归一化为 `default`。
- 主体身份可以为空，适配尚未接入登录态的阶段。
- IP、设备标识和 User-Agent 属于审计线索，不是当前证据中用于鉴权的字段。
- endpoint 有默认教材文本检索路径。
- 审计 JSON 不写入空字段。

### 检索事件

- `queryId` 是查询和前端 trace 关联的核心键。
- `hitCount` 来自实际响应，不由请求 limit 推导。
- `elapsedMs` 不允许以负数写入。
- 命中排名按响应顺序从 `1` 开始。
- 空命中列表仍会写入查询汇总记录，但不会插入命中行。

### JDBC 写入

- 查询汇总和命中记录必须在同一事务中成功提交。
- 写入失败会回滚当前 JDBC 事务并抛出异常。
- 可空字符串字段使用 SQL NULL 写入。
- `page_no` 使用显式 NULL 处理。
- 检索策略会去除首尾空白，并截断到 64 个字符，以适配数据库字段长度。
- 请求上下文或命中证据 JSON 序列化失败会抛出 `IllegalStateException`。
- 数据库中的非法 JSON 在查询还原时会抛出异常，而不是静默返回空对象。

### 审计查询

- 空白 `queryId` 不访问数据库。
- 不存在的 `queryId` 由控制器转换为 404。
- 命中记录按排名升序还原。
- 查询依赖 query ID 关联查询和命中记录；当前控制器证据未显示额外的租户或主体鉴权过滤。

## 主要文件

- `RetrievalRequestContext.java`：请求调用方、设备线索和 endpoint 的规范化及审计 Map 转换。
- `RetrievalAuditEvent.java`：一次检索的汇总审计事件及构建逻辑。
- `RetrievalAuditHit.java`：单条命中记录的审计模型。
- `RetrievalAuditSink.java`：审计写入端口。
- `RetrievalAuditLookup.java`：按 query ID 查询审计事件的端口。
- `CompositeRetrievalAuditSink.java`：向多个写入 Sink 广播审计事件。
- `JdbcRetrievalAuditSink.java`：MySQL 事务写入、查询、JSON 编解码及字段边界处理。
- `RecentRetrievalAuditStore.java`：近期审计记录的内存存储候选实现。
- `RetrievalAuditConfiguration.java`：审计组件装配入口。
- `RetrievalAuditController.java`：审计详情 HTTP API。
- `V1__metadata_and_retrieval_audit.sql`：检索查询表和命中表的数据库结构来源。

## 扩展点

### 增加新的写入后端

实现 `RetrievalAuditSink` 即可接入新的记录后端，例如日志系统、消息队列或专用可观测性平台。新增实现应保持 `record(RetrievalAuditEvent)` 的完整事件语义，尤其是 query 级汇总信息与 hit 级证据的关联。

### 替换查询实现

实现 `RetrievalAuditLookup` 可以替换 JDBC 查询来源，例如：

- 近期内存查询。
- 只读分析库。
- 外部审计服务。
- 测试环境中的内存替身。

控制器无需改变。

### 增加审计字段

优先在领域事件中增加字段，再同步调整：

1. `RetrievalAuditEvent` 或 `RetrievalAuditHit`。
2. JDBC INSERT 和 SELECT。
3. JSON 序列化与反序列化。
4. 数据库迁移脚本。
5. 相关查询返回模型。

请求上下文中的可选线索适合继续放在 `request_context_json`；需要稳定查询、索引或聚合的核心字段则更适合使用独立数据库列。

### 扩展多租户和访问控制

`tenantId` 已进入请求上下文和查询汇总记录，当前默认值为 `default`。后续引入多机构隔离时，查询接口不能只依赖 `queryId`，还应结合认证主体和租户范围校验，避免已知 query ID 被跨租户读取。当前控制器源码证据中尚未体现这层过滤。

### 增强失败处理

组合 Sink 当前采用“任一 delegate 失败即抛出”的策略。若未来需要降低审计故障对检索主链路的影响，可以在组合层引入异步队列、重试或失败事件记录，但必须同时保留可观测的投递状态，避免把降级实现变成静默丢失。
